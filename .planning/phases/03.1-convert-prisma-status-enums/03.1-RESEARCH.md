# Phase 3.1: Convert Prisma Status Fields to Enums - Research

**Researched:** 2026-01-27
**Domain:** Prisma 7.3 PostgreSQL enum migration with existing data
**Confidence:** HIGH
**Last Verified:** 2026-01-27 (Official Prisma Documentation + GitHub)

## Summary

Converting string-based status fields to Prisma enums in PostgreSQL requires a carefully staged migration due to how PostgreSQL handles type conversion. The project uses Prisma 7.3.0, which is the latest stable release (released January 21, 2026) and has resolved the mapped enum bugs present in 7.0-7.2.

Three status fields need conversion:
1. `Quiz.status` (draft, preview_required, published, archived)
2. `Quiz.showResults` (after_submit, after_due, manual)
3. `QuizAttempt.status` (in_progress, submitted, graded)

The key challenge is that PostgreSQL cannot automatically cast TEXT columns to ENUM types - the migration must explicitly use `USING column::EnumType` syntax. Prisma's auto-generated migrations do not include this clause, so manual migration editing is required.

**Primary recommendation:** Use single-step migration with manual SQL editing to add `USING` clause for each column conversion. The expand-and-contract pattern is overkill for this case since the existing string values exactly match the target enum values.

## Architecture Patterns

### Prisma Schema Enum Definition

```prisma
// Define enums at the top of schema.prisma
enum QuizStatus {
  draft
  preview_required
  published
  archived
}

enum ShowResultsOption {
  after_submit
  after_due
  manual
}

enum AttemptStatus {
  in_progress
  submitted
  graded
}

// Use in models
model Quiz {
  // ...
  status      QuizStatus         @default(draft)
  showResults ShowResultsOption  @default(after_submit)
  // ...
}

model QuizAttempt {
  // ...
  status      AttemptStatus      @default(in_progress)
  // ...
}
```

### Prisma 7 Enum Behavior (Verified via Official Docs)

Per the [Prisma 7 Upgrade Guide](https://www.prisma.io/docs/orm/more/upgrade-guides/upgrading-versions/upgrading-to-prisma-7):

**Mapped Enums Reverted to v6 Behavior:** The mapped enum implementation initially planned for Prisma ORM v7 was reverted. Generated TypeScript enum values use schema names rather than mapped values.

Example:
```prisma
enum SuggestionStatus {
  PENDING   @map("pending")
  ACCEPTED  @map("accepted")
}
```

Generated TypeScript:
```typescript
export const SuggestionStatus = {
  PENDING: 'PENDING',   // NOT 'pending'
  ACCEPTED: 'ACCEPTED', // NOT 'accepted'
} as const
```

**Important:** `SuggestionStatus.PENDING` evaluates to `"PENDING"`, not `"pending"`. The mapping occurs at the database level only.

### Migration SQL Pattern

```sql
-- 1. Create enum types
CREATE TYPE "QuizStatus" AS ENUM ('draft', 'preview_required', 'published', 'archived');
CREATE TYPE "ShowResultsOption" AS ENUM ('after_submit', 'after_due', 'manual');
CREATE TYPE "AttemptStatus" AS ENUM ('in_progress', 'submitted', 'graded');

-- 2. Convert columns with USING clause (Prisma won't generate this automatically)
ALTER TABLE "Quiz"
  ALTER COLUMN "status" TYPE "QuizStatus" USING "status"::"QuizStatus",
  ALTER COLUMN "showResults" TYPE "ShowResultsOption" USING "showResults"::"ShowResultsOption";

ALTER TABLE "QuizAttempt"
  ALTER COLUMN "status" TYPE "AttemptStatus" USING "status"::"AttemptStatus";
```

### TypeScript Usage After Migration

```typescript
// Prisma client exports enum values
import { QuizStatus, ShowResultsOption, AttemptStatus } from '@/generated/prisma';

// Type-safe comparisons
if (quiz.status === QuizStatus.published) { ... }

// Type-safe assignments
await prisma.quiz.update({
  where: { id: quizId },
  data: { status: QuizStatus.draft }
});

// Zod schema updates
const UpdateQuizSettingsSchema = z.object({
  showResults: z.nativeEnum(ShowResultsOption).optional(),
});
```

### Anti-Patterns to Avoid

- **Direct string assignment after migration:** Use `QuizStatus.draft` not `'draft'`
- **Skipping USING clause:** Migration will fail with "cannot be cast automatically" error
- **Adding new enum values mid-migration:** PostgreSQL only allows appending, not inserting
- **Using @map expecting runtime mapped values:** Prisma 7.3 uses schema names in TypeScript, not mapped values

## Don't Hand-Roll

| Problem | Don't Build | Use Instead | Why |
|---------|-------------|-------------|-----|
| Type validation | Custom validation functions | Prisma native enum | Database-level constraint + TypeScript types |
| Status string constants | `const QUIZ_STATUS = { ... }` | `QuizStatus` enum from Prisma | Single source of truth, auto-generated |
| Migration rollback | Manual reverse SQL | Prisma migrate with rollback migration | Maintain migration history |

**Key insight:** Prisma generates TypeScript enums that can be imported directly. After migration, all `'draft'` string literals should become `QuizStatus.draft` for full type safety.

## Common Pitfalls

### Pitfall 1: Prisma Migration Doesn't Include USING Clause

**What goes wrong:** `prisma migrate dev` generates migration that fails with "column cannot be cast automatically to type"
**Why it happens:** PostgreSQL requires explicit cast instruction for TEXT to ENUM conversion
**How to avoid:** After running `prisma migrate dev --create-only`, manually edit the migration.sql to add `USING column::EnumType` to each ALTER COLUMN statement
**Warning signs:** Error message mentions "HINT: You might need to specify USING"

### Pitfall 2: Enum Value Mismatch

**What goes wrong:** Migration fails because existing data contains values not in the enum
**Why it happens:** Database has unexpected values (typos, legacy data)
**How to avoid:** Before migration, run validation query:
```sql
SELECT DISTINCT status FROM "Quiz"
WHERE status NOT IN ('draft', 'preview_required', 'published', 'archived');
```
**Warning signs:** "invalid input value for enum" error

### Pitfall 3: Default Value Timing

**What goes wrong:** Migration applies default before data conversion, causing type mismatch
**Why it happens:** Order of operations in ALTER TABLE matters
**How to avoid:** Order migration steps as: (1) create enum type, (2) alter column type with USING, (3) set new default
**Warning signs:** "column default cannot be cast to type" errors

### Pitfall 4: Index Recreation

**What goes wrong:** Indexes on status columns may need rebuilding after type change
**Why it happens:** PostgreSQL indexes are type-specific
**How to avoid:** Prisma handles this automatically, but verify indexes exist after migration
**Warning signs:** Slow queries on status columns after migration

## Code Examples

### Pre-Migration Validation Script

```typescript
// scripts/validate-enum-migration.ts
import prisma from '@/lib/prisma';

async function validateEnumMigration() {
  // Check Quiz.status
  const invalidQuizStatus = await prisma.$queryRaw`
    SELECT DISTINCT status FROM "Quiz"
    WHERE status NOT IN ('draft', 'preview_required', 'published', 'archived')
  `;

  // Check Quiz.showResults
  const invalidShowResults = await prisma.$queryRaw`
    SELECT DISTINCT "showResults" FROM "Quiz"
    WHERE "showResults" NOT IN ('after_submit', 'after_due', 'manual')
  `;

  // Check QuizAttempt.status
  const invalidAttemptStatus = await prisma.$queryRaw`
    SELECT DISTINCT status FROM "QuizAttempt"
    WHERE status NOT IN ('in_progress', 'submitted', 'graded')
  `;

  console.log('Invalid Quiz.status:', invalidQuizStatus);
  console.log('Invalid Quiz.showResults:', invalidShowResults);
  console.log('Invalid QuizAttempt.status:', invalidAttemptStatus);

  const hasIssues =
    (invalidQuizStatus as unknown[]).length > 0 ||
    (invalidShowResults as unknown[]).length > 0 ||
    (invalidAttemptStatus as unknown[]).length > 0;

  if (hasIssues) {
    console.error('Data validation failed! Fix invalid values before migration.');
    process.exit(1);
  }

  console.log('All data valid for enum migration.');
}

validateEnumMigration();
```

### Code Update Pattern: Server Actions

```typescript
// Before (string literals)
status: 'draft',

// After (enum values)

```

### Code Update Pattern: Zod Schemas

```typescript

// After
```
