# Phase 3.2: Centralize QuestionType Definition - Research

**Researched:** 2026-01-27
**Domain:** TypeScript Type Centralization / Refactoring
**Confidence:** HIGH

## Summary

This phase addresses tech debt where QuestionType is defined in multiple locations, leading to maintenance burden and bypassing compile-time type checking. The codebase currently has:

1. **UI Layer**: `QuestionType` union type in `question-renderer.tsx` (9 values)
2. **AI Layer**: `QuestionType` Zod enum in `question-generation.ts` (6 values)
3. **Grading Layer**: Accepts raw `string` parameter with switch cases handling 9+ variants

The standard approach uses TypeScript's `as const` assertion with `typeof array[number]` pattern, which this codebase already implements in `src/lib/storage/images.ts`. This provides a single source of truth that works for both runtime validation and compile-time type checking.

**Primary recommendation:** Define `QUESTION_TYPES` const array in `types.ts`, derive `QuestionType` from it, add `isValidQuestionType()` type guard, then update consumers.

## Architecture Patterns

### Recommended Pattern: Const Array with Derived Type

This pattern is already used in the codebase at `src/lib/storage/images.ts`:

```typescript
// Source: C:\Users\matth\Desktop\Fun-with-code\src\lib\storage\images.ts lines 14-23
export const ALLOWED_IMAGE_TYPES = [
  'image/jpeg',
  'image/png',
  'image/gif',
  'image/webp',
] as const;

export type AllowedImageType = (typeof ALLOWED_IMAGE_TYPES)[number];

export function isAllowedImageType(
  contentType: string
): contentType is AllowedImageType {
  return ALLOWED_IMAGE_TYPES.includes(contentType as AllowedImageType);
}
```

### Target Structure for types.ts

```typescript
// Canonical source of truth for question types
export const QUESTION_TYPES = [
  'multiple_choice',
  'true_false',
  'true_false_justify',  // Alias for true_false with justification
  'fill_in_blank',
  'fill_blank',           // Alias for fill_in_blank
  'essay',
  'short_answer',
  'show_work',
  'matching',
] as const;

// Derived type from const array
export type QuestionType = (typeof QUESTION_TYPES)[number];

// Type guard for runtime validation of strings from database/API
export function isValidQuestionType(value: string): value is QuestionType {
  return QUESTION_TYPES.includes(value as QuestionType);
}
```

### Why This Pattern

| Benefit | Explanation |
|---------|-------------|
| Single source of truth | Array defines all valid values once |
| Compile-time safety | TypeScript infers union from array |
| Runtime validation | Type guard validates strings from external sources |
| Iteration support | Can iterate over `QUESTION_TYPES` for UI dropdowns, etc. |
| IDE autocomplete | Union type provides autocomplete for all values |

### Anti-Patterns to Avoid

- **Separate const and type definitions**: Leads to drift between runtime and compile-time values
- **String enums**: Less flexible than const arrays (no iteration, no `includes()` support)
- **Accepting raw `string` in function signatures**: Bypasses compile-time checking

## Don't Hand-Roll

| Problem | Don't Build | Use Instead | Why |
|---------|-------------|-------------|-----|
| Type validation | Custom switch/if chains | `isValidQuestionType()` type guard | Centralized, reusable, TypeScript-native |
| Type arrays for UI | Duplicate arrays in components | Import `QUESTION_TYPES` | Single source of truth |
| Zod schema for question type | Separate `z.enum()` definition | `z.enum(QUESTION_TYPES)` | Reuses central const |

## Common Pitfalls

### Pitfall 1: Forgetting Type Aliases

**What goes wrong:** The codebase uses aliases (`fill_blank` for `fill_in_blank`, `true_false_justify` for `true_false`). Missing these breaks existing data.

**Why it happens:** Looking only at `types.ts` discriminated union types (6 values) instead of actual usage (9 values).

**How to avoid:** Include ALL values from:
- `question-renderer.tsx` QuestionType (9 values)
- `grading.ts` switch cases (9+ with aliases)
- AI schema `QuestionType` (6 values)

**Warning signs:** Tests fail with "Unknown question type" errors for aliases.

### Pitfall 2: Breaking the Discriminated Union Pattern

**What goes wrong:** `QuestionOptions` uses `type` field as discriminant. If `QuestionType` includes values not in `QuestionOptions.type`, type narrowing breaks.

**Why it happens:** Confusion between `QuestionType` (9 values including aliases) and `QuestionOptions.type` discriminant (6 canonical values).

**How to avoid:** Keep `QuestionType` as the superset. Document that aliases (`fill_blank`) map to canonical types (`fill_in_blank`) in `QuestionOptions`.

**Warning signs:** TypeScript errors about non-exhaustive switches.

### Pitfall 3: Import Cycles

**What goes wrong:** Circular dependencies if `question-renderer.tsx` imports from `types.ts` while `types.ts` imports from components.

**Why it happens:** The codebase intentionally uses component-local types (see prior decisions: "Component-local option types to avoid circular dependencies").

**How to avoid:** `types.ts` must have zero imports from components. Components import from `types.ts`, never the reverse.

**Warning signs:** Build errors about circular dependencies, or runtime errors about undefined exports.

### Pitfall 4: Zod Schema Sync

**What goes wrong:** The AI layer's `QuestionType` Zod enum in `question-generation.ts` gets out of sync with the central definition.

**Why it happens:** Forgetting to update the AI schema when centralizing.

**How to avoid:** Update `question-generation.ts` to use `z.enum(QUESTION_TYPES)` or import from central location. Note: AI schema only uses 6 types - this is intentional (AI generates only these types).

**Warning signs:** AI-generated questions have types not recognized by other parts of system.

```typescript
// Source: Pattern from src/lib/storage/images.ts adapted for question types

// =============================================================================

/**
 * Canonical list of all supported question types.
 * Includes aliases (fill_blank, true_false_justify) for backward compatibility.
 */
export const QUESTION_TYPES = [
  'multiple_choice',
  'true_false',
  'true_false_justify',
  'fill_in_blank',
  'fill_blank',
  'essay',
  'short_answer',
  'show_work',
  'matching',
] as const;

/**
 * Union type of all valid question types.
 * Derived from QUESTION_TYPES for single source of truth.
 */
export type QuestionType = (typeof QUESTION_TYPES)[number];

/**
 * Type guard to validate strings from database/API as valid QuestionType.
 * Use this when receiving questionType from external sources.
 */
export function isValidQuestionType(value: string): value is QuestionType {
  return QUESTION_TYPES.includes(value as QuestionType);
}
```

## State of the Art

| Old Approach | Current Approach | When Changed | Impact |
|--------------|------------------|--------------|--------|
| String literals in multiple files | `as const` with derived types | TypeScript 3.4+ (2019) | Single source of truth |
| Manual type guard arrays | Derived from same const | TypeScript 3.4+ | Eliminates drift |
| Separate runtime/compile-time | Unified const + type | Industry standard | Simpler maintenance |

**Current in this codebase:**

- Question types still use old approach (manual definitions)
